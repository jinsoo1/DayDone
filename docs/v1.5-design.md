# v1.5 설계 — 국제화 기반 (한국어 그대로 출시)

> 2026-08-31 작성. **대표 기능 없음.** v1.6.0 일본어 출시를 위한 바닥 공사만 한다.
> 결정 배경은 CLAUDE.md §15 "🌏 해외 배포" 참고.
>
> **이 릴리즈의 성공 기준: 유저가 아무 변화도 못 느끼는 것.**
> 문구 하나 안 바뀌고, 숫자 하나 안 바뀐다. 새 기능도 없다.

---

## 0. 왜 두 번에 나누나 (핵심 결정)

문자열 추출 + 번역 + 새 언어 QA 를 한 번에 하면 **회귀 범위가 앱 전체**가 된다.
1인 개발에서 가장 위험한 형태다.

`stringResource` 치환은 문구 하나만 어긋나도 유저 눈에 바로 띈다. 그런데 그걸
일본어와 동시에 하면, 문제가 생겼을 때 **추출이 잘못된 건지 번역이 잘못된 건지**
구분할 수가 없다. 그래서 추출만 먼저 한국 유저로 검증한다.

> ⚠️ **1.5.0 은 실제로 배포해야 의미가 있다.** 머지만 해두고 1.6.0 까지 들고 있으면
> 검증을 못 받아서 나눈 이유가 사라진다.

## 2. 안 하는 것 (전부 1.6.0 이후)

- 일본어 번역, 일본어 카테고리 사전, 일본 큰지출 달 표
- 일본 스토어 등록정보·스크린샷·개인정보처리방침
- 영어 (§3 급여 주기 문제부터 결정해야 함 — CLAUDE.md §15)
- **인앱 언어 선택 UI** ← 아래 이유

### 인앱 언어 선택기를 넣지 않는 이유

1.5.0 은 한국어 하나만 들어 있으므로 **고를 게 없다.** 1.6.0 에서 `values-ja/` 가
생기면 안드로이드가 시스템 언어를 보고 알아서 고른다 — 선택기 없이도 동작한다.

넣으려면 비용이 붙는다: `MainActivity` 가 `ComponentActivity` 이고 **AppCompat 의존성이
없다.** Android 12 이하에서 per-app language 를 지원하려면 AppCompat 을 새로 넣어야
하는데(minSdk 28), 의존성 하나를 언어 선택기 하나 때문에 추가하는 건 과하다.
Android 13+ 는 `localeConfig` 만 넣으면 **시스템 설정에서** 앱별 언어를 바꿀 수 있다.

→ **1.5.0 은 `localeConfig` 만 넣고 선택기는 만들지 않는다.** 필요하면 1.6.0 에서 재검토.

## 3. 작업 순서

> ⚠️ **순서가 곧 안전장치다.** 초안은 presentation 추출(3-2)을 먼저 두고 domain 을 뒤에
> 뒀었는데, 그러면 **가장 위험한 구간을 가장 지친 시점에** 하게 된다. 그리고 domain 이
> 만드는 문구가 presentation 으로 내려오면서 추출 대상 자체가 바뀌므로, 먼저 추출해둔
> 화면을 다시 건드리게 된다(같은 파일 두 번 커밋 = 회귀 추적 불가).
>
> **그래서 아래로 뒤집는다: 의존성이 깊은 것부터, 테스트가 지켜주는 것부터.**
> presentation 567개의 기계적 치환은 맨 마지막이다 — 그때쯤이면 문구가 더 안 움직인다.

| 단계 | 내용 | 규모 | 테스트가 지켜주나 |
|---|---|---:|---|
| 3-1 | 기반 (locale 설정 · Lint) | — | — |
| 3-2 | **포맷터 경계** (`MoneyFormat` · 요일) | 2파일 | 새로 추가 |
| 3-3 | **알림 4종 sealed 화** | 18 | ✅ 기존 |
| 3-4 | **`BuildMonthlyReportUseCase` sealed 화** | 47 | ✅ 기존 |
| 3-5 | **enum `labelRes` 치환** | 16 | 컴파일러 |
| 3-6 | 잔여 domain (`GetTodayDateChips` 등) | ~20 | 일부 |
| 3-7 | presentation 추출 | 567 | ❌ 눈 + Lint |
| 3-8 | data / widget / notification | 60 | ❌ |

### 3-1. 기반 (0.5일)

- `resConfigs("ko")` → 1.6.0 에서 `("ko","ja")`. 지금 로케일 설정이 **아예 없다**.
- `res/xml/locales_config.xml` + 매니페스트 `android:localeConfig`
- ~~Lint `HardcodedText` 켜기~~ → **안 먹는다.** 켜보니 지적이 0건이었는데, 좋은 신호가
  아니라 이 규칙이 **XML 레이아웃 전용**이기 때문이다. 이 앱엔 XML 화면이 없다.
  → `checkHardcodedKorean` **Gradle 태스크**로 대체했다. 주석·로그를 뺀 Kotlin 소스에
  한글 문자열 리터럴이 남아 있으면 실패한다. 허용 목록은 **"번역하면 안 되는 것"**
  (백업 폴더 경로·통화 접미사)과 **"1.6.0 에서 재작성할 것"**(카테고리 사전·배달
  키워드)뿐이다.
- 린트가 실제로 값어치를 한 곳은 따로 있었다 — `StringFormatMatches`. 추출 스크립트가
  숫자 인자에도 `%1$s` 를 써서 12건이 떴다(`%1$d` 로 수정). **켜두면 다음에도 잡힌다.**

### 3-2. 포맷터 경계 — 모든 문장이 여기에 의존한다 (0.5일)

**이게 1번인 이유**: 3-3·3-4 에서 sealed 타입으로 바꾼 문장을 presentation 에서 다시
조립할 때 전부 금액 포맷터를 부른다. 포맷터가 나중에 바뀌면 그 조립을 다시 훑어야 한다.

- **`presentation/util/MoneyFormat.kt`** — 현재 `NumberFormat(Locale.KOREA) + "원"` 하드코딩.
  통화 기호 **위치** 개념을 도입한다 (한국 `1,234원` 뒤 / 일본 `¥1,234` 앞 또는 `1,234円` 뒤).
  톤상 일본은 **円**이 부드럽다. 1.5.0 에선 한국 값만 꽂아 출력이 1원도 안 바뀌게 한다.
  → **한국어 출력 회귀 테스트를 함께 넣는다** (`1234567L` → `"1,234,567원"`, 0·음수 포함).
- **요일 포맷터** — 지금 같은 로직이 **3벌**이다:
  `BuildMonthlyReportUseCase.toKorean()` · `GetTodayDateChipsUseCase.toKoreanWeekText()` ·
  `LedgerViewModel.toKoreanWeek()`. 하나로 합치고 로케일을 타게 한다.
  (`java.time` 의 `DayOfWeek.getDisplayName(SHORT, locale)` 이 ko/ja 모두 올바른 1글자를 준다)
- ⚠️ domain 의 `formatMoney`/`toKorean` 은 **여기서 지우지 않는다.** 3-5 에서 문장이 통째로
  sealed 타입이 되면 호출부가 사라지면서 자연히 죽는다. 먼저 지우면 중간 상태가 안 컴파일된다.

### 3-3. 알림 4종 sealed 화 (1일) ✅ 테스트가 지켜줌

`BuildEveningNotificationUseCase`(6) · `BuildMorningNotificationUseCase`(5) ·
`BuildUpcomingDeductionNoticeUseCase`(4) · `BuildHeldPurchaseNotificationUseCase`(3).

**리포트보다 먼저 하는 이유**: 규모가 작고(18개) `NotificationContent` 라는 경계 타입이
**이미 있다.** sealed 전환 패턴을 여기서 확정한 뒤 47개짜리 리포트(3-4)에 적용한다.

- `NotificationContent.title/body: String` → 무엇을 말할지 나타내는 sealed 타입 + 인자.
- **`target` 은 그대로 둔다** — 목적지는 표시 문구가 아니라 동작이고, CLAUDE.md §12 가
  "합쳐지면 갈 화면도 달라진다"고 못 박은 자산이다.
- **저녁 제목 우선순위**(무지출 축하 > 내일 출금 > 기록 안내)와 **합치기 규칙**은 판정이지
  문구가 아니다. 전환 후에도 `BuildEveningNotificationMergeTest` 가 이걸 검증해야 한다.
  문자열 비교 → 타입 비교로만 바꾼다.
- 조립 지점은 워커(`NotificationWorker`) — Context 가 있으므로 `getString()` 으로 만든다.

### 3-4. `BuildMonthlyReportUseCase` sealed 화 (1.5~2일) ⚠️ 최대 구간

47개. **제안 규칙만 13종**이고 페이스 헤드라인이 진행 중/결산으로 갈린다.

```kotlin
sealed interface ReportAdvice {
    data class OverBudgetWithTopCategory(
        val overAmount: Long,
        val category: ExpenseCategory,
        val categoryTotal: Long,
    ) : ReportAdvice
    data class SavingRateGood(val percent: Int) : ReportAdvice
    ...
}
```

- 이모지(`"💰"`)는 규칙에 붙은 식별자이므로 **sealed 타입에 남기거나 presentation 매핑표로**.
  리소스로 빼지 않는다.
- `formatMoney`·`toKorean` 호출부가 전부 사라진다 → 3-2 에서 남겨뒀던 private 함수를
  **여기서 지운다.**
- `BuildMonthlyReportUseCaseTest` 는 페이스 구간(±7%p GOOD/ON_TRACK/FAST)과
  **지난 기간 대비(같은 dayIndex 비교)** 를 지킨다. 이 두 개는 삭제 금지.
- 조립은 `ReportScreen`/`ReportViewModel`. 3-7 에서 `ReportScreen`(65개)을 추출할 때
  **이 조립 문구까지 함께** 리소스로 나가므로, 3-4 단계에선 한글 리터럴이 presentation 으로
  잠시 **이사만** 오는 상태가 된다(정상 — 총량은 그대로).

### 3-5. 단순 라벨 enum → `@StringRes labelRes` (0.5일)

`label: String` → `@StringRes labelRes: Int`. **Int 상수라 순수 JVM 테스트가 그대로 돈다**
(`R.string.*` 는 값이 필요 없고 참조만 되므로). emoji 는 리소스로 빼지 않는다 — 번역 대상이 아니다.

```kotlin
enum class ExpenseCategory(@StringRes val labelRes: Int, val emoji: String) {
    PET(R.string.category_pet, "🐾"),
    ...
}
```

> ⚠️ **이 단계가 3-3 이 아니라 3-5 인 이유** (착수하고 나서 발견해서 순서를 고쳤다).
> 실측해보니 `label: String` 을 들고 있는 enum 은 `ExpenseCategory` **하나뿐**이고
> (`FutureExpenseCategory`·`FutureExpenseRepeat`·`NoSpendMode` 는 라벨이 없다 —
> 문구가 `VaultScreen` 의 `when` 에 있어서 3-7 에서 처리된다),
> 그 `label` 의 호출부 2곳 중 하나가 **`BuildMonthlyReportUseCase` 의 제안 문구 안**이다:
> `"'${topCategory.category.label}'(...)부터 돌아보면…"`.
>
> 즉 enum 을 먼저 바꾸면 그 문장이 컴파일되지 않고, 임시로 한글 라벨 표를 UseCase 에
> 복사해 넣어야 한다 — **지우려고 시작한 것을 한 벌 더 만드는 셈**이다.
> 리포트를 sealed 로 바꾸면(3-4) 그 자리는 카테고리를 **값으로** 넘기게 되므로,
> 리포트 다음에 하면 남는 호출부가 `ReportScreen` 한 곳뿐이라 그냥 끝난다.

### 3-6. 잔여 domain (0.5일)

`GetTodayDateChipsUseCase`(7, 날짜 칩 라벨 — 3-2 요일 포맷터로 대부분 해소) ·
`GetBigSpendMonthNoticeUseCase`(13) · `PreJoinSpendUseCases`(2) · 1개짜리 4곳.

- `GetBigSpendMonthNoticeUseCase` 는 **로케일별 표를 꽂을 자리**를 만든다. 한국 표(설·추석
  음력, 2030년까지)는 그대로. 일본은 명절이 전부 양력 고정이라 표 자체가 필요 없어진다
  (1월 お正月 / 4월 新生活 / 5월 GW+自動車税 / 8월 お盆 / 12월 年末年始) — 연 1회 갱신
  부담이 오히려 사라진다. **데이터는 1.6.0**, 여기선 구조만.
- `ClassifyExpenseCategoryUseCase` — 사전을 갈아끼울 수 있는 구조로만. 한국 사전 740개는
  손대지 않는다. 매칭 규칙(가장 긴 키워드 승리, `EXACT_ONLY`)은 언어 무관이라 유지.

### 3-7. presentation 추출 (567개 / 24파일, 3~4일)

**이제 문구가 더 안 움직이므로 기계적으로 민다.** 파일 크기 순, **묶음 단위 커밋**.
회귀가 나면 어느 화면인지 바로 좁혀진다.

> **손으로 하지 않았다.** 567개를 사람이 옮기면 오타가 반드시 섞인다. 파이썬 스크립트로
> ① 주석 밖 문자열 리터럴만 찾고 ② `"a" + "b"` 로 이어붙인 문장은 **한 문장으로 합치고**
> (번역자가 조각이 아니라 문장을 봐야 한다) ③ `${...}` 보간을 `%1$s` 로 바꿔 인자로
> 넘긴다. 키는 **한글 로마자**(개정 로마자 표기법)로 만든다 — `today_042` 같은 번호 키는
> 번역자에겐 상관없지만 코드에서 무엇을 가리키는지 알 수 없다.
>
> ⚠️ **스크립트가 건드리면 안 되는 것을 두 번 건드렸다.** `primary:Download/DayDone/백업`
> (SettingsScreen)과 `FOLDER_BACKUP`/`FOLDER_EXCEL` 상수(BackupRepositoryImpl). 한글이
> 들어갔다는 이유로 리소스가 됐는데, 번역되면 기존 유저의 복원 목록이 빈다. 되돌리고
> **그 자리에 이유를 주석으로 박아뒀다** — 다음에 누가 또 스크립트를 돌릴 것이기 때문이다.
> `checkHardcodedKorean` 허용 목록에도 같은 이유로 들어가 있다.
>
> 스크립트가 못 보는 것: `.format()` 호출(문자열 리터럴이 아니라 인자로 들어간다),
> `sealed class` 생성자 인자처럼 Composable 밖에 있는 것(`HomeTab.label` →
> `@StringRes labelRes`), Glance 위젯(`androidx.compose.ui.res.stringResource` 가 아니라
> `androidx.glance.LocalContext` 를 쓴다).

| 순서 | 파일 | 개수 |
|---|---|---:|
| 1 | `TodayScreen.kt` | 141 |
| 2 | `VaultScreen.kt` | 81 |
| 3 | `ReportScreen.kt` | 65 (+3-5 에서 이사 온 문구) |
| 4 | `SettingsScreen.kt` | 64 |
| 5 | `MonthlyScreen.kt` | 50 |
| 6~ | Onboarding(31) · HeldPurchases(26) · PurchaseDecisionSheet(25) · ChallengeSettingsSheet(23) · NotificationSettings(20) · 나머지 | |

**키 규칙**: 단일 `strings.xml` + 화면 접두어(`today_`, `vault_`, `report_`) + XML 주석으로
구역 나누기. 파일을 쪼개면 개발자는 편하지만 **번역자가 568개를 순서대로 훑기 어렵다.**
번역을 외주로 낼 것이므로 번역자 기준으로 정한다.

플레이스홀더는 `<xliff:g>` 로 감싸고, 뜻이 모호한 문구엔 번역자용 주석을 단다.
(예: "권장 금액"이 상한이 아니라 권장이라는 뉘앙스 — CLAUDE.md 용어 절)

- **금고 예시 문구** — 프리셋 시스템이 아니라 `VaultScreen` 의 placeholder 3줄
  ("예: 자동차세 40만 원")이다. 리소스로 빼면 끝. 일본은 自動車税·車検으로 바뀐다.

### 3-7-b. ViewModel 문구 (0.5일)

ViewModel 6개가 화면에 그대로 나갈 문구를 만든다. `@ApplicationContext` 를 주입하고
`getString` 으로 조립한다.

UiState 에 타입으로 올려 화면에서 조립하는 게 3-3·3-4 와 같은 방향이지만, 그건 화면
배선을 전부 다시 만드는 일이라 **"변화가 0인 것을 증명하는" 이 릴리즈의 범위를 넘는다.**
ViewModel 은 이미 presentation 이고 순수 JVM 테스트가 걸려 있지도 않아서 Context 주입이
잃는 게 없다.

- ⚠️ `TodayUiState.selectedDateTitle` 의 기본값 `"오늘 내역"`은 `data class` 라
  `getString` 을 못 부른다. 빈 값으로 두고 ViewModel 이 채운다 — 로딩 직후 한 프레임뿐이다.

### 3-8. data / widget / notification (60개, 0.5일)

- 엑셀 시트명("지출"·"고정지출")·헤더·`daydone-내역` 파일명, 백업 에러 문구
- ⚠️ **백업 폴더 경로 `Download/DayDone/…` 는 로케일화 금지** —
  `ListBackupFilesUseCase` 가 이 경로로 조회한다. 바꾸면 기존 유저의 복원 목록이 빈다.
  **파일명만** 바꾼다.
- ⚠️ 위젯은 시스템이 갱신 시점을 정하므로 언어 변경 직후 반영이 늦을 수 있다(정상).

## 4. 절대 건드리지 않는 것 (회귀 방지선)

문자열 작업 중에 "이왕 하는 김에" 를 허용하지 않는다. 이 릴리즈의 가치는
**변화가 없다는 것을 증명하는 것**이라서다.

- **계산 로직 일절 손대지 않음** (권장 금액·이월·리포트·챌린지·보류함)
- **Room 스키마 무변경** — DB v7 유지, 마이그레이션 없음
- **`BACKUP_VERSION = 1` 유지** — 백업 JSON 에 한글 키가 없는 것을 확인했다.
  (한글은 전부 엑셀 시트명·에러 문구·파일명이었다.)
- 백업 폴더 경로
- UI 레이아웃·색상·간격

## 5. 테스트

**기존 유닛 테스트 134개가 그대로 통과하는 것이 1.5.0 의 주 검증 수단이다.**
(현재 142개 — `MoneyFormat` 4개, `SentenceFormat` 4개 추가. 실패 0.)

⚠️ **테스트가 지켜주는 범위는 domain 까지다.** 3-7·3-8 의 추출은 컴파일과
`checkHardcodedKorean` 만 통과하면 되고, **문구가 실제로 그대로인지는 눈으로 봐야 한다.**
스크립트가 옮긴 623개 중 하나가 어긋나도 테스트는 초록이다.

- 3-3·3-4 리팩터링에서 테스트를 고쳐야 한다면 **문구 비교를 타입 비교로 바꾸는 것만 허용**한다.
  판정 로직 검증(구간·우선순위·경계값)은 반드시 남긴다.
  예: `assertEquals("오늘 지갑이 쉬었어요 🎉", title)` → `assertEquals(EveningTitle.NoSpendCelebration, content.title)`
- **추가**: `MoneyFormat` 한국어 출력 회귀 테스트 (`1234567L` → `"1,234,567원"`)
- **수동 확인(필수)**: 전 화면 훑기(문구 누락 = 빈 문자열/키 노출), 알림 6종, 위젯 2종,
  엑셀 내보내기, **백업 저장·복원 목록**(폴더 경로가 안 바뀌었는지 — 여기가 유일하게
  데이터를 잃을 수 있는 자리다), 리포트 제안 문구, 월 탭 큰 지출 줄.

## 6. 릴리즈

- `versionCode 9` / `versionName "1.5.0"`
- 스토어 문구(listing·promo·개인정보처리방침) **변경 없음**
- **공지**: 낼지 말지 판단 필요. 유저에게 달라지는 게 없다.
  - 안 내는 쪽: 변화가 0인데 공지를 내면 열어본 사람이 허탈하다(§13).
  - 내는 쪽: 1.1.0 에 "내부 개선" 전례가 있다. 낸다면 **한 줄**로.
  - → **권장: 내지 않는다.** 1.6.0 일본어 출시 때 함께 언급하는 게 자연스럽다.
    (한국 유저에게 "곧 일본어" 는 알릴 가치가 없다.)

**실측: 커밋 12개.** 3-7 은 스크립트 덕에 예상(3~4일)보다 훨씬 짧았고, 대신 3-3·3-4
(알림·리포트 sealed 화)가 이 릴리즈의 실제 무게중심이었다.

**공수: 개발 7~10일** (3-7 이 절반). 번역 외주는 1.5.0 이 끝난 뒤 병렬로 착수 가능 —
`strings.xml` 이 나오는 즉시 넘길 수 있다.
